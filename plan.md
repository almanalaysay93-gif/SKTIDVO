## 14. F-SYNC-01 — Google Sign-In + Sheet sync (Rev 3)

### 14.1 Architecture
```
App (local store = source of truth)
  ├─ js/auth/gis.js         web + iOS PWA: Google Identity Services (google.accounts.id) → ID token (JWT)
  ├─ js/auth/native.js      [PHASE 2] Android Capacitor: native Google sign-in plugin → ID token (§14.6)
  ├─ js/sync/meta.js        pure: stamp(updatedAt, deviceId, deleted), deviceId generation
  ├─ js/sync/merge.js       pure: LWW merge + tombstones
  ├─ js/sync/queue.js       pure+storage: outbox, backoff(attempt, rand)
  ├─ js/sync/api.js         POST text/plain JSON {idToken, op, ...} to Apps Script /exec
  └─ js/sync/engine.js      orchestration: push → pull → merge → store, status events
           │ HTTPS (no Sheets API, no Google client secret)
Apps Script web app (Execute as: owner, Access: Anyone) — apps-script/Code.gs
  verifyToken → authorize → validate → rateLimit → LockService → read/write sheet tabs
Google Sheet (owners only, Restricted)
```
Rules: the sheet ID lives only in Script Properties, never in the client. The client knows only the `/exec` URL and the OAuth client ID (both public).

### 14.2 Data model changes (store.js, migration v2)
- Every collection record: `+ updatedAt:number(ms)`, `+ deviceId:string`, `+ deleted:boolean`, `+ syncedAt:number|absent` (absent = never acknowledged by the server). Profile, schedule, settings and checklist become single records `{id:'profile'...}` in sync payloads (local shape unchanged).
- New keys (additive): `skti.v1.deviceId` (random 128-bit hex via `crypto.getRandomValues`), `skti.v1.syncState` `{cursor, lastSyncAt, consentVersion, consentAt, email}`, `skti.v1.outbox` `[ {entity, id} ]`, plus Rev 2 keys `a2hsDismissed`, `lastBackupAt`.
- Deletes become tombstones (`deleted:true`, hidden by every getter) instead of splice; purged after the retention window (OQ-11).
- Legacy approvals (OQ-14 resolved): `migrateV2()` resets every lab/limit with `status:'approved'` to `pending` (approvals are identified only by Google email); share@spmcdvo.net must re-approve.
- Restore (advisory A5): clearing `syncedAt` on restored records lives in `store.importAll` (js/store.js, called from features/backup.js), so every import path gets it.
- Migration `migrateV2()` at boot: stamps existing records with `updatedAt = record ts || now`, own `deviceId`, `deleted:false`, and NO `syncedAt` (all pre-sync data counts as never-synced, so it is pushed on first sync); deletes `skti.v1.clinician` (FR025); idempotent; covered by A023/A027 fixture tests.
- Backup JSON: includes the new fields; import still forces labs/limits `pending` (FR008).
- Entities (12): profile, weights, intake, sessions, medications, medLogs, checklist, hdBp, dietLog, customFoods, labs, limits.
- NOT synced (with reason): `foodCache` (regenerable lookup cache); USDA API key (device setting, the user's own key); `deviceId`, `syncState`, `outbox`, `a2hsDismissed`, `lastBackupAt` (device-local state); ID token (memory only).

### 14.3 Sync algorithm
1. Gate: signed in AND `consentVersion` == current AND online; otherwise status = off/offline.
2. Push: read outbox → batch ≤ 200 records / ≤ 400 KB → `op:'push'`. Server applies LWW per (email, entity, id) using `updatedAt`, tie-break `deviceId`, and returns accepted ids plus server-normalized records (e.g. labs forced pending). Remove acked ids from the outbox.
3. Pull: `op:'pull', since: cursor` → server returns rows with `serverSeq > cursor` for that email (all entities), plus the new cursor. Merge with `merge(local, remote)` (pure LWW); write without re-enqueueing.
4. New device: cursor = 0 → full restore (FR018).
5. Backoff: `delay = min(15 min, 1 s * 2^attempt) * (0.5 + rand/2)`; reset on success; 401 → re-auth prompt, no retry storm; 429 → honor server `retryAfter`.
6. Triggers: boot, `online`, `visibilitychange` visible, 3 s debounce after a local write, manual "Sync now".
7. Clock skew: the server stores `serverUpdatedAt` for audit; LWW uses client `updatedAt`. `validatePayload` rejects any record whose `updatedAt` is > now + 24 h (unit test under A022/A029), so one bad clock cannot win every future conflict.
8. Stale device after tombstone purge (PR025, corrected Rev 3.2 for PR036 / C005).
   - Each local record carries `syncedAt` (ms of the last server ack; absent = never pushed). Set on push ack and on records received by pull.
   - The server keeps a per-email `purgedBefore` watermark (time up to which tombstones were purged).
   - A pull with `since` < `purgedBefore`, or a push from a client whose `lastSyncAt` < `purgedBefore`, returns `cursor_too_old`.
   - The client then (1) pulls a full snapshot, (2) drops ONLY local records that HAVE `syncedAt` and are absent from the snapshot (they were deleted and purged elsewhere), (3) re-pushes every record WITHOUT `syncedAt`, flagged `neverSynced:true`, regardless of `updatedAt`, plus outbox records with `updatedAt` ≥ `purgedBefore`.
   - The server applies the `purgedBefore` filter (ignore unknown ids with `updatedAt` < watermark) only to pushes NOT flagged `neverSynced`; `neverSynced` records are accepted as new rows (LWW still applies if the id exists).
   - Dirty synced records (PR037): a record with `syncedAt` whose `updatedAt` > `syncedAt` (edited offline after its last ack) that IS present in the snapshot is re-pushed regardless of the watermark and resolved by normal LWW against the snapshot copy. If it is absent from the snapshot (deleted + purged elsewhere), it is dropped like any other synced record.
   - Backup restore (PR038): `importBackup` clears `syncedAt` on every restored record, so restored data counts as never-synced. A later resync cannot drop it, and it is re-pushed with `neverSynced`.
   - Result: offline-created data is never lost (C005), and a previously synced, deleted record cannot come back.
   - Why not keep tombstones forever: the sheet has a 10M-cell cap; the watermark keeps growth bounded at the cost of one snapshot pull.
   - Tests (T050 client, T051 server): "stale device after purge does not resurrect", "never-synced old create survives resync", "previously synced deleted record does not resurrect", "dirty synced record edited offline is re-pushed and resolved by LWW", "restored backup records survive resync".

### 14.7 Apps Script (apps-script/)
- Files: `Code.gs` (doPost/doGet routing, sheet IO), `lib.gs` (pure functions: `verifyClaims(claims, now, allowedAuds)`, `authorize(op, email, target)`, `validatePayload(body)`, `lww(a,b)`, `forcePendingLabs(rec, isClinician)`, `rateLimitDecision(count, limit)`). `lib.gs` is also exported for node tests via a tiny shim (tests/apps-script.test.js loads it with `vm`).
- Token verification: `UrlFetchApp.fetch('https://oauth2.googleapis.com/tokeninfo?id_token=' + t)` (Google validates the signature). Why tokeninfo, not local JWKS: Apps Script has no maintained JWT/RS256 library and hand-rolled signature checks are error-prone; tokeninfo is Google-maintained. Exposure: tokeninfo is rate-limited and adds latency, which the CacheService token cache (keyed by SHA-256 of the token until `exp`) reduces (advisory A1) → `verifyClaims`: `aud` ∈ allowed, `iss` ∈ {accounts.google.com, https://accounts.google.com}, `exp*1000 > now`, `email_verified === 'true'||true`. Cache valid tokens in CacheService by SHA-256(token) until exp to save quota.
- Request: `POST /exec` body text/plain JSON (avoids CORS preflight); response `ContentService` JSON `{ok, code, data}`. The browser follows a redirect to `script.googleusercontent.com`.
- Sheet layout (created by `setup()` run once by the owner): tabs per entity with columns `email | id | updatedAt | deviceId | deleted | serverSeq | serverUpdatedAt | json`; plus `consent` (email, version, at), `audit` (at, email, op, count, result), `meta` (serverSeq counter). Rows keyed by (email, id); column order is fixed; readable by owners.
- Concurrency: `LockService.getScriptLock().waitLock(20000)` around writes.
- Rate limit: CacheService counter `rl:<email>:<minute>`, incremented inside a short `LockService` script lock (≤ 2 s wait; if the lock times out, the request proceeds and the limit is treated as SOFT). Limit 60 req/min/email, 600/day/email (proposed) → 429.
- Validation: body ≤ 400 KB; ≤ 200 records; entity whitelist; field types; strings ≤ 2 KB; reject unknown ops.
- Delete my data (`op:'deleteMe'`): removes all rows for the email in every tab, logs to audit, returns counts.
- Retention (OQ-11 resolved): daily time-driven trigger (1) deletes all rows of a patient whose last activity (max `serverUpdatedAt`) is older than 1 year, unless deleted earlier via FR027, and (2) purges tombstones per the watermark design (§14.3 step 8), advancing `purgedBefore`. RETENTION is a fixed constant (365 days), not a setting.
- Quotas (consumer free tier; values to VERIFY at T052 against Google's current quota page): URL Fetch calls/day, script runtime 6 min/execution, simultaneous executions, triggers total runtime. - CSP update (scoped per Google GIS guidance): `script-src 'self' https://accounts.google.com/gsi/client; frame-src https://accounts.google.com/gsi/; connect-src 'self' https://api.nal.usda.gov https://world.openfoodfacts.org https://script.google.com https://script.googleusercontent.com https://accounts.google.com/gsi/; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://accounts.google.com/gsi/style`.
- SW: never cache `script.google.com`, `script.googleusercontent.com`, `accounts.google.com`, `oauth2.googleapis.com` (network-only; sign-in needs online).
- Tokens in memory only; never logged; never in backup/localStorage. Accepted risk (advisory A2): a stolen bearer ID token can be replayed until `exp` (~1 h); mitigated by memory-only storage, HTTPS only, short lifetime, and the server binding all access to the token email.
- No client secret anywhere; the Web OAuth client has no secret in use; Script Properties hold the sheet ID, client IDs and clinician list. Repo grep check (T068).
- Server treats every client field as untrusted: email comes ONLY from the verified token, never from the body (except `op:'approve'` target patient, which is allowed for the clinician only).
- Abuse: rate limit, payload caps, audit tab, Restricted sheet sharing (A031).
- Privacy (RA 10173): consent text versioned; notice covers purpose, data list, recipients (clinic; developer co-owner access disclosed), retention (OQ-11), rights (access via export, deletion via FR027), contact; clinic approves (T064).
